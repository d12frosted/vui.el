#+TITLE: vui.el benchmarks

A characterization suite for vui's render performance. The point is not
micro-numbers but finding where vui starts to hurt.

* Running

#+begin_src sh
eldev emacs --batch -l benchmarks/vui-bench.el -f vui-bench-run
#+end_src

Or load =benchmarks/vui-bench.el= and =M-x vui-bench-run=. The report
goes to stdout (batch) or the echo area / =*Messages*= (interactive).

These are not part of =eldev test= - they are slow and noisy, and not
meant to gate CI.

* Scenarios

| Scenario          | What it measures                                            |
|-------------------+------------------------------------------------------------|
| Initial render    | Mount cost vs item count                                   |
| Re-render         | Full re-render cost vs item count (tree unchanged)         |
| Single-item update | Cost of changing one item in a list of N                  |
| Streaming append  | Per-line re-render as a transcript grows                   |
| Update throughput | Raw re-render floor for a trivial UI                       |
| Widgets           | Full re-render cost vs interactive widget (button) count   |
| Tables            | Re-render cost vs rows, vs columns, and string vs vnode cells |
| Table width mode  | char vs pixel measurement cost (#121), where the build has the switch |
| Responsive layout | =vui-flex= with vs without =:wrap=, =vui-grid=, and composed multi-line rows (#134) |

* What to expect (the shape, not the numbers)

vui re-renders by rebuilding the buffer (or an inline region) from the
component tree each cycle, so the durable findings are about scaling
shape, not absolute milliseconds (which depend on the machine):

- *Plain text/content scales linearly* and is cheap - thousands of rows
  render in single-digit milliseconds.
- *A small change costs a full re-render.* Updating one item in a list
  of N costs about the same as re-rendering all N - there is no partial
  patching yet (see issue #82).
- *Streaming append is the sharp case.* Appending one line and
  re-rendering is O(current length), so streaming M lines into a growing
  transcript is O(M^2) overall. This is the case where a marker-based
  append (insert at the end, no full rebuild) wins, and the main
  motivation for incremental rendering (#82).
- *Buttons are cheap and linear.* Buttons, checkboxes and selects render as
  =button.el= text buttons: no widgets, no markers, roughly a flat ~3us/row
  in batch, only a little dearer than plain text. This was not always so.
  They used to be =widget.el= push-buttons, and every =widget-create= left
  two live markers in the buffer; Emacs adjusts every live marker on each
  insert, so N buttons cost O(N^2) to build and tens of thousands could crash
  Emacs (#107). #108 detached the markers (linear, ~8us/row); the text-button
  migration then dropped widgets for buttons entirely (~3us/row). Editable
  fields are the one thing still built on =widget.el= (it has no text-input
  equivalent), but you rarely have many at once.

- *Tables are the measurement-heavy path.* Column widths are recomputed from
  scratch on every render, so every cell is measured several times per pass and
  cost tracks cells (rows x columns), not rows: at 500 rows the per-column cost
  settles at ~3.8ms from 5 columns up (a touch higher at 2, where the
  per-table overhead has fewer columns to amortize over). A 5-column table runs
  about 6x a plain-text list of the same row count, and vnode cells cost about
  2x string cells, because measuring a vnode means rendering it into a temp
  buffer while a string is measured directly.

  This is why the width primitive itself matters here and nowhere else.
  =string-pixel-width= costs roughly 23x what =string-width= does per call, so
  pixel-based alignment (#121) lands squarely on this scenario. Note the
  =Table width mode= numbers only appear on a build that has the switch, and
  that in batch the two modes render identical text (a tty frame is one pixel
  per column) while still costing different amounts - decide the default from a
  GUI frame.

Re-run after performance changes and compare; the suite exists so those
changes can be justified and regressions caught.
